주니어 개발자에게 에이전트를 쓰는 문제는 “얼마나 많이 위임할 것인가”가 아니다. 더 중요한 질문은 **위임한 뒤에도 내 판단력이 자라는가**다.

Memex에서 정리한 주니어 에이전트 워크플로우의 출발점은 간단하다. 구현 속도는 AI에게 빌리되, 문제 정의와 위험 판단, 완료 판정, 핵심 경로의 이해는 사람이 계속 소유한다.

## 구현보다 먼저 지켜야 할 것

AI에게 코드를 맡기면 결과는 빠르게 나온다. 하지만 검증과 이해까지 함께 넘기면, 당장은 생산성이 올라간 것처럼 보여도 다음 작업에서 사용할 수 있는 정신 모델이 남지 않는다. 설명할 수 없는 코드는 아직 내 역량으로 계산하지 않는다는 기준이 필요하다.

사람이 직접 소유할 일은 네 가지다.

- 무엇을 왜 바꾸는지 정하는 문제 정의와 스펙
- 실패했을 때 피해가 얼마나 큰지 판단하는 위험도 분류
- 실제로 동작하는지 확인하는 완료 판정
- 핵심 경로를 자신의 말로 다시 설명하는 이해 확인

반대로 코드베이스 탐색 지도, 반복적인 구현, 테스트 초안, 문서화와 blind-spot 검사는 AI에게 넘기기 좋은 일이다. 디버깅과 설계 트레이드오프는 AI의 가설과 사람의 체크포인트를 결합하는 공저 영역으로 남긴다.

## 이슈 하나를 끝내는 7단계 루프

### 1. 스펙을 직접 쓴다

5~15분 동안 목표 동작을 한 문장으로 적는다. 입력·출력·저장 경계, 실패 경로, 이번 작업에서 하지 않을 일을 함께 적으면 AI가 문제를 불필요하게 키우기 어렵다.

### 2. 먼저 지도를 요청한다

구현부터 시키지 말고 관련 요청 흐름, 주요 파일, 저장 경계, 실패 경계를 설명해 달라고 한다. 이때 모든 파일을 깊게 읽을 필요는 없다. 반드시 이해해야 하는 코드와 계약만 확인하면 되는 코드를 분리해 달라고 요청한다.

### 3. 위험도를 나눈다

깊게 볼 코드, 입력·출력 계약만 볼 코드, 나중에 봐도 되는 코드를 나눈다. 모든 줄을 같은 깊이로 읽는 것은 주니어에게도 AI에게도 비효율적이다. 위험도가 높은 경로에 사람의 주의력을 집중한다.

### 4. 계획을 승인한 뒤 구현을 맡긴다

AI는 plan mode로 시작한다. 계획이 처음 쓴 스펙보다 커졌다면 승인하기 전에 잘라낸다. 범위가 맞는 것을 확인한 뒤 보일러플레이트, 얇은 wrapper, 반복적인 폼과 테스트 초안을 위임한다.

### 5. 작성자와 검사자를 분리한다

코드를 만든 AI의 “완료” 선언만으로 끝내지 않는다. 위험도가 높은 부분은 줄 단위로 직접 리뷰하고, 나머지는 입력·출력·실패 시 동작이라는 계약을 확인한다. 가능하면 별도 세션이나 `/code-review` 같은 다른 검사자에게 blind-spot pass를 맡긴다.

### 6. 검증 게이트를 통과시킨다

최소한 세 가지를 확인한다.

1. 실제 실행이 성공하는가
2. 실패 케이스 하나에서 의도한 오류가 나는가
3. 기존 경로 하나가 깨지지 않았는가

테스트·린트·빌드가 있으면 사용하고, 없다면 실행 가능한 가장 작은 확인을 만든다. 검증 기준이 없는 자율 루프는 반복이 아니라 맹목적인 재시도에 가깝다.

### 7. 이해 부채를 기록하고 닫는다

마지막으로 핵심 경로를 내 말로 설명한다. 설명하지 못한 부분은 실패가 아니라 다음 학습 항목인 이해 부채로 기록한다. 이번 주에는 그중 하나를 골라 가장 작은 from-scratch 재현으로 갚는다.

## 무엇을 통째로 맡기고, 무엇을 같이 할까

결정 기준은 AI가 잘하는지가 아니라, 결과가 명확하고 검증 가능하며 실패를 되돌릴 수 있는지다.

| 작업 | 협업 방식 | 이유 |
| --- | --- | --- |
| README 초안, 반복 코드, 테스트 뼈대 | 통째로 위임 | 완료 조건이 비교적 명확하다 |
| 요청 흐름 탐색, 실패 원인 가설 | 같이 한다 | 값과 맥락은 직접 확인해야 한다 |
| 아키텍처, 제품 방향, 운영 리스크 | 공저 | 방향과 책임이 사람에게 있다 |
| 완료 판정, 배포, merge | 직접 결정 | 결과의 책임과 위험이 크다 |

## 하네스는 작게 시작한다

주니어에게 필요한 최소 하네스는 거대한 자동화 플랫폼이 아니다. 프로젝트의 `CLAUDE.md`나 `AGENTS.md`에 실행·테스트 명령, 아키텍처 한 단락, 위험 경계를 적고, plan → 승인 → 실행 → 리뷰 루프를 반복하는 정도면 충분하다.

도구 권한은 보수적으로 시작하고, 테스트·린트 hook을 붙인다. verifier agent, planner/dev/reviewer 프로필, 멀티 worktree 오케스트레이션은 단일 세션에서 검증 게이트가 습관이 된 뒤에 추가한다. 검증 기준이 없는 상태에서 에이전트 수만 늘리면 약한 검증을 병렬화할 뿐이다.

## 다음 이슈에 바로 적용하는 법

다음 실제 이슈 하나를 골라 7단계 루프를 한 번만 끝까지 돌린다. 끝난 뒤 “무엇을 AI에게 넘겼는가”보다 **내가 설명하지 못한 것은 몇 개인가**를 센다. 그 숫자가 현재 워크플로우의 가장 유용한 지표다.

워크플로우를 완벽하게 설계한 뒤 시작할 필요는 없다. 실제 이슈에서 막힌 지점만 고치면 된다. 목표는 운영체제를 만드는 것이 아니라, 사람의 이해 속도와 에이전트의 실행 속도가 다시 만나는 작은 반복을 만드는 것이다.
